## T01
结论：
SLO（服务级别目标）就是"我们承诺的服务质量底线"，错误预算是这条底线之下"允许出错的额度"。两者的关系可以概括为一句话：**SLO 决定预算有多少，错误预算决定我们还能不能冒险**。这是 SRE 中把"可靠性"和"发布速度"放在同一个账本里算账的核心机制。

---

步骤/分析：

**1. 先用一个生活类比理解三兄弟**

- **SLI（服务级别指标）**：像"体温计读数"。它是用户真实感知到的服务质量数字，比如"100 个请求里有多少个成功""延迟在 200ms 以内的请求占多少比例"。
- **SLO（服务级别目标）**：像"我们定的目标体温上限"。比如"一个月内 99.9% 的请求都成功"。它不是拍脑袋定的，而是对 SLI 设的一个目标值。
- **错误预算（Error Budget）**：像"允许生病的额度"。如果目标是 99.9%，那就意味着还有 0.1% 的请求可以失败——这 0.1% 就是错误预算，是我们"允许不可靠"的部分。

**2. 错误预算怎么算？**

课程知识库中的原文说法是：**"错误预算等于允许的不可靠比例，例如 99.9% 可用性目标对应 0.1% 的预算。"**

也就是说：
- 错误预算 = 100% − SLO（目标可用性）
- SLO 定得越严（比如 99.99%），预算越少（只有 0.01%），容错空间越小；
- SLO 定得松一些（比如 99%），预算越多（1%），容错空间越大。

**3. 它们的关系：一个"可靠性账本"**

知识库中明确了预算的两种使用场景：

- **预算充足时 → 可以提高发布速度**。因为还有"额度"可以消耗，这时候可以放心上线新功能、做实验性变更，把预算花在创新上。
- **预算持续耗尽时 → 应暂停高风险变更，优先处理可靠性**。一旦把年度（或月度）的"出错额度"用完了，就要踩刹车：停止高风险发布，全力做稳定性工作，直到预算"回血"。

这背后的理念是：**不可能同时做到"100% 可靠"和"快速迭代"**，错误预算就是这两者之间的"货币"，让团队用数据而不是吵架来决定"现在该冲还是该稳"。

**4. 一个配套的实践建议（面向课程学习）**

知识库还提到：**告警应尽量基于用户影响和错误预算消耗率，而不是单一 CPU 阈值**。意思是——与其盯着"CPU 到 90% 就报警"，不如盯"错误预算正在以多快的速度被消耗"。如果预算消耗很快，说明 SLO 有被击穿的风险，这才是更值得触发行动的信号。这条思路也是 AIOps 告警降噪的一个方向。

---

示例或练习：

- 某服务 SLO = 99.9%，则错误预算 = 0.1%。假设一个月请求总量为 1000 万次，那么一个月内允许失败的请求数约为 1 万次（0.1%）。
- 如果月中已经失败了 9000 次，预算只剩 1000 次——此时团队应该"谨慎行事"，暂缓高风险发布；如果只失败了 1000 次，预算还很充足，可以正常迭代。

---

资料依据：
- 课程资料《SRE 与可观测性：SLI、SLO、错误预算和遥测信号》（02-sre-observability.md）："SLI 是用户可感知服务行为的量化指标……SLO 是一个时间窗口内对 SLI 的目标。错误预算等于允许的不可靠比例，例如 99.9% 可用性目标对应 0.1% 的预算。预算充足时可以提高发布速度；预算持续耗尽时应暂停高风险变更并优先处理可靠性。"
- 同一资料中关于告警的说明："告警应尽量基于用户影响和错误预算消耗率，而不是单一 CPU 阈值。"

说明：生活类比（体温计、生病额度）和 1000 万次请求的算例是为了帮助你理解而补充的讲解，属于面向理解的说明，不是知识库原文；"可靠性 vs 迭代速度的权衡"这一层意思是对"预算充足/耗尽时行动不同"这一事实的合理延伸解读。

## T02
结论：
可观测性的四大黄金信号是**延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）**。课程知识库明确列出了这四类信号，并提到面向请求的服务常用 RED（Rate、Errors、Duration）三个指标来落地；不过知识库对"每个信号具体反映什么问题"没有展开原文，下面我结合课程其他资料做解释，并会明确标注哪些是资料原话、哪些是补充讲解。

---

步骤/分析：

**1. 资料原文先放在这里（事实）**

- "黄金信号包括延迟、流量、错误和饱和度。面向请求的服务常使用 RED：Rate、Errors、Duration。"
- 配套的补充事实：课程故障案例中提到"**错误率正常不代表无故障（延迟类故障先于错误出现）**"——这说明不同信号反映的问题维度不同，不能只看错误一个信号。

**2. 四个信号分别反映什么问题（补充讲解，方便理解）**

| 信号 | 通俗理解 | 反映的系统问题 |
| --- | --- | --- |
| **延迟** | 用户等多久才有响应 | 反映"快不快"。延迟升高说明处理链路变慢，可能是慢查询、锁等待、网络抖动等。注意延迟往往**先于错误出现**，是早期预警信号。 |
| **流量** | 有多少请求在打进来 | 反映"忙不忙、需求有多大"。流量异常（突增/突降）说明负载在变化，可能是促销、爬虫攻击、上游故障导致请求中断等。 |
| **错误** | 有多少请求失败 | 反映"对不对"。错误率升高说明功能不可用或处理失败，比如 5xx、超时、依赖服务拒绝连接。 |
| **饱和度** | 系统资源用了多少、还有多少余量 | 反映"够不够"。饱和度接近 100% 说明容量见顶，比如 CPU、内存、磁盘、连接池耗尽，是"即将撑不住"的前兆，往往会导致延迟恶化和错误增加。 |

**3. 四个信号之间的"因果链条"（合理推断）**

这四者不是孤立的，典型的恶化顺序是：**流量上升 → 饱和度上升 → 延迟上升 → 错误上升**。比如大促流量暴涨，先把 CPU 打满（饱和度），请求开始排队（延迟变高），最终超时失败（错误增加）。所以排查故障时，沿这条链从前往后看，往往能更快定位瓶颈。这一点属于对四个信号关系的合理解读，课程资料没有逐条写出，但案例中"延迟类故障先于错误出现"与其一致。

**4. 落地建议（面向实践）**

- 四个信号应**同时监控**，不能只看错误率（案例一就是错误率正常、P99 延迟飙升，最后定位到慢查询）。
- 告警优先级上，资料建议"**基于用户影响和错误预算消耗率**"而不是单一阈值，例如用"P99 延迟超过 SLO 阈值"比"CPU > 90%"更贴近用户体验。
- 饱和度类指标（磁盘、连接数）比较适合简单阈值，但对流量这类季节性波动强的指标，简单阈值容易误报（这也是课程异常检测章节的观点）。

---

示例或练习：

**案例对照（来自课程案例库）**：支付服务 P99 延迟从 120ms 升至 1.8s，错误率正常，CPU 正常。
- 这里**延迟**信号最先报警；
- **错误**信号正常，说明还没到失败阶段；
- 最终根因是新增查询缺索引导致全表扫描——本质上是**饱和度**（数据库扫描开销）先出了问题，表现为延迟恶化。
- 复盘要点正是："错误率正常不代表无故障"。

---

资料依据：
- 《SRE 与可观测性：SLI、SLO、错误预算和遥测信号》（02-sre-observability.md）："黄金信号包括延迟、流量、错误和饱和度。面向请求的服务常使用 RED：Rate、Errors、Duration。"
- 《故障诊断案例演练库》（10-incident-case-studies.md）："错误率正常不代表无故障（延迟类故障先于错误出现）；慢查询是发布回归的高频根因。"

说明：上表中"每个信号反映什么问题"、四信号因果链及告警落地建议，属于基于上述资料的补充讲解与合理推断，知识库未逐条展开原文，请以课堂讲义和 Google SRE 原书（https://sre.google/books/）为准。

## T03
结论：
**告警风暴**指一次真实故障触发几十到几百条告警同时爆发，把值班人员淹没、让人找不到真正根因的现象。课程知识库给出的**第一步处置思路是"先聚合再分析"**：用告警聚合/事件关联把风暴压缩成少量"事故候选"，而不是让值班人员一条条去看。

---

步骤/分析：

**1. 什么是告警风暴（资料原文）**

知识库描述得很具体：
> "一次真实故障往往触发几十到几百条告警：数据库慢 → 上游接口超时 → 网关 5xx → 业务告警同时爆发。直接把所有告警交给值班人员会淹没真正的根因。"

这说明告警风暴的本质是：**一个根因故障沿着调用链级联传播，在多个层级同时触发告警**，于是"一条故障"看起来像"几百个问题"。课程案例里更直观：夜间 200+ 条告警，值班人员无从下手。

**2. 常见成因（结合资料归纳）**

| 成因类别 | 具体说明 | 资料依据 |
| --- | --- | --- |
| **级联传播** | 故障沿依赖链扩散：数据库慢 → 上游接口超时 → 网关 5xx → 业务告警同时爆发，同一根因在不同层级重复报警 | 07 章原文 |
| **拓扑汇聚点故障** | 共享数据库/缓存等被多个服务共同依赖的组件出问题，所有下游一起告警 | 07 章、10 章案例 |
| **告警规则缺乏抑制** | 下游告警在根因告警存在时没有降级/抑制，导致同类信息重复轰炸 | 10 章案例处置 |
| **误报与告警疲劳** | 规则设置不当（如单一阈值对波动型指标误报），告警过多导致值班人员忽略全部告警 | 06 章异常检测 |

其中"级联传播 + 拓扑汇聚点"是告警风暴最典型的技术成因，"缺乏抑制规则"和"误报多"是放大因素。

**3. 课程建议的第一步处置思路（重点）**

知识库明确：**告警聚合/事件关联**是第一道工序，分两步压缩：

1. **按时间窗与拓扑邻接分组**——把同一时间窗内、在调用拓扑上相邻的告警归为一组；
2. **按文本相似度合并同源告警**——通过日志模板化（如 Drain 算法把变量替换成通配符）把内容相近的告警合并成"事故候选"。

最终目标：把"告警风暴"聚合成**少量"事故候选"**，再交给值班人员或 RCA 工具分析，而不是直接淹没人类。

**4. 配套的进一步建议（供学习参考）**

- 聚合之后，**优先看拓扑"汇聚点"**——被多个异常服务共同依赖的组件（数据库、缓存）是高置信根因候选（07 章原文）。
- 事后治理上，课程案例给出的方向包括：**告警规则增加拓扑抑制**（下游告警在根因告警存在时降级），以及把磁盘等告警阈值前移、提前预警（10 章案例）。
- 评价上，聚合效果可以用**Top-k 命中率、MTTI（平均定位时间）**等指标衡量（07 章原文）。

---

示例或练习：

**课程案例 3：告警风暴掩盖真实故障**
- 现象：夜间 200+ 条告警，值班人员无从下手。
- 排查：按拓扑聚合发现告警源头集中在一个数据库实例，其余为超时级联；日志模板化后归并为 3 类事件。
- 根因：磁盘写满导致数据库拒绝写入，上游全部级联超时。
- 处置：清理磁盘 + 扩容磁盘告警阈值前移；告警规则增加拓扑抑制。
- 复盘要点：告警风暴**先聚合再分析**；拓扑汇聚点（共享数据库/缓存）是高置信根因候选。

---

资料依据：
- 《根因分析：告警风暴、服务拓扑与因果推断》（07-root-cause-analysis.md）："一次真实故障往往触发几十到几百条告警……告警聚合/事件关联先做两步压缩：按时间窗与拓扑邻接分组，再按文本相似度（日志模板化，如 Drain 算法把变量替换为通配符）合并同源告警，把'告警风暴'聚合成少量'事故候选'。"
- 《故障诊断案例演练库》（10-incident-case-studies.md）案例 3："告警风暴先聚合再分析；拓扑汇聚点（共享数据库/缓存）是高置信根因候选。"
- 《异常检测》（06-anomaly-detection.md）："误报过多会导致'告警疲劳'，值班人员开始忽略全部告警"——用于解释放大因素。

说明：上表中"常见成因"的分类归纳（级联传播、拓扑汇聚、缺乏抑制、误报疲劳）是我基于上述资料整理的结构化表述，其中"级联传播与拓扑汇聚"有原文直接支持，"抑制规则缺失""误报放大"来自案例处置与异常检测章节的对应原文；关于"第一步处置是聚合"的表述有明确原文支持。

## T04
结论：
从 AIOps 角度看，这个现象组合（延迟升高 + 5xx 升高 + 吞吐下降 + **CPU 只有 35%**）的关键信号是：**服务自身并不在"计算"上吃紧，而是在"等待"**。CPU 低说明大概率不是本机算力饱和，根因更可能指向**外部依赖（数据库/缓存/下游服务）、连接与线程资源耗尽、或发布回归**。下面按课程推荐的"现象 → 可能原因 → 证据 → 安全排查 → 后续建议"组织分析。

---

步骤/分析：

## 一、现象解读（先读信号）

| 信号 | 含义 | 结合 CPU 35% 的解读 |
| --- | --- | --- |
| P99 延迟升高 | 用户等得越来越久 | 请求可能在排队、在等下游、在等锁/连接 |
| 5xx 错误率升高 | 部分请求已经失败 | 故障已进入"级联/后期"阶段（延迟通常先于错误出现，见案例 1 复盘要点） |
| 吞吐量下降 | 单位时间完成的请求变少 | 与错误上升互相印证：大量请求没跑完就失败了 |
| CPU 仅 35% | **服务没有在满负荷计算** | 排除"计算密集导致 CPU 饱和"这一常见方向，指向等待型故障 |

课程资料明确：告警应基于用户影响和错误预算消耗率，而不是单一 CPU 阈值——本例恰好说明"CPU 正常 ≠ 系统健康"。

## 二、可能原因（按置信度排序，最多 3 个主候选）

依据课程 05 章要求"输出至多三个候选，每个含支持证据、反证、待验证数据"，结合知识库案例给出：

**候选 1：共享依赖（数据库/缓存）故障或过载 —— 拓扑汇聚点问题（高置信）**
- 支持证据：CPU 低但延迟、错误、吞吐同时恶化，典型"等下游"形态；07 章指出拓扑中"汇聚点"（共享数据库、缓存）是高置信根因候选。
- 可对照案例：
  - 案例 2（缓存雪崩）：缓存命中率 95%→20%，请求集中回源数据库，连接池打满 → 大量 5xx、延迟飙升，与本例几乎同构；
  - 案例 3（磁盘写满）：数据库拒绝写入 → 上游全部级联超时；
  - 案例 1（慢查询）：缺索引全表扫描拖慢数据库。
- 反证：如果数据库/缓存指标全部正常，则该候选不成立。

**候选 2：服务自身"等待资源"耗尽 —— 连接池/线程池/锁/GC（中高置信）**
- 支持证据：CPU 低而请求排队，典型的等待型饱和：数据库连接池耗尽、HTTP 客户端连接池耗尽、线程池队列堆积、锁竞争、GC 停顿等。
- 案例 4 的教训：内存泄漏→周期性重启也会表现为性能骤降，但本例未提重启，需用内存趋势验证。
- 反证：若池使用率、队列长度、GC 指标均正常，则排除。

**候选 3：发布/变更回归（需变更记录佐证）**
- 支持证据：案例 1 中"变更记录对应 20 分钟前的版本发布"是强线索；新查询缺索引、新配置导致依赖调用变化都可能造成延迟+错误。
- 反证：若故障时间与最近变更窗口不重合、回滚不能缓解，则降低置信度。

其他需保留的低概率方向（补充推断）：网络层问题（丢包/重传、DNS）、上游限流或 WAF 拦截、下游服务自身故障引发的级联。

## 三、需要补充验证的证据（全部只读）

1. **时间线**：发布/配置变更、告警、用户报障、故障起始的先后（05 章：先按统一时区排列，标来源与置信度）。
2. **数据库**：慢查询日志、连接池使用率、锁等待、磁盘空间与 IO、磁盘是否写满（对应案例 1/2/3）。
3. **缓存**：命中率、回源流量、key 过期时间分布、缓存实例是否重启（对应案例 2）。
4. **服务内部**：线程池/连接池队列深度、GC 频率与停顿时长、内存增长趋势（对应案例 4 的泄漏曲线）、网络重传/丢包。
5. **错误模式**：5xx 具体是哪一类——504 超时（等下游）、503 限流/过载、502 上游不可达、连接被拒绝，直接指向不同根因。
6. **时序先后**：各指标谁先异常（07 章：先异常的指标指向根因组件；注意相关≠因果，发布、定时任务是常见假相关诱因）。
7. **拓扑**：该服务的上下游依赖关系是否与现网一致（07 章警告：拓扑数据过期是常见错误）。

## 四、安全排查顺序（低风险只读优先，严禁先做写操作）

按 05 章建议的诊断顺序（影响面 → 变更相关性 → 依赖拓扑 → 资源饱和 → 错误模式 → 历史相似事故）：

1. **先看时间线**：故障起始 vs 最近发布/配置变更是否重合（零风险，信息量最大）。
2. **看依赖汇聚点**：数据库、缓存的只读指标（命中率、连接池、慢查询、磁盘）——这一步大概率能命中候选 1/2。
3. **看服务内部等待指标**：线程池/连接池队列、GC、内存趋势、网络。
4. **用链路追踪定位延迟集中在哪个 span**：时间花在本服务还是下游（案例 1 正是靠追踪发现时间集中在数据库 span）。
5. **归类 5xx 错误模式**，并结合日志模板化后的错误类型判断。
6. **给出至多 3 个候选根因**，每个附支持证据、反证、置信度和待验证假设（05 章要求），只读验证后再收敛。
7. **写操作必须走审批**：回滚、限流、预热、重启、清理磁盘等高风险动作需审批+最小权限+幂等+回滚准备（01 章、03 章护栏）；本案例中"清磁盘/回滚发布"这类动作不应未经确认直接执行。

## 五、后续建议（区分缓解与永久修复）

- **缓解（先恢复用户体验）**：视候选而定，如限流保护、热点 key 临时预热（案例 2）、回滚可疑发布（案例 1）。

结论：
用 PromQL 计算 HTTP 5xx 错误率，核心思路是**"5xx 请求速率 ÷ 总请求速率"**，并且必须用 `rate()` 处理计数器（counter）类型的指标，而不能直接对累计值做除法。课程知识库确认 Prometheus 是"事实标准的时序指标系统、PromQL 查询"，但**具体 PromQL 语法未在课程资料中展开**，以下示例属于通用工具知识讲解，语法细节以官方文档（知识库列出的 https://prometheus.io/docs/ ）为准。

---

步骤/分析：

**1. 前置概念（为什么这么写）**

- HTTP 请求指标通常是 **counter（只增不减的累计值）**，例如 `http_requests_total`，带 `code`（状态码）、`method`、`handler` 等标签。
- 要算"错误率"，必须先通过 `rate(指标[时间窗口])` 把累计值转换成**每秒速率**，否则直接除会得到累计比例，反映不出当前状态。
- 错误率公式本质上是黄金信号中 **RED 的 Errors ÷ Rate**（知识库提到面向请求的服务常用 RED：Rate、Errors、Duration）。

**2. 分步写出查询**

假设指标名为 `http_requests_total`，`code` 标签为状态码字符串：

- 5xx 请求速率（匹配 500–599）：
  ```
  sum(rate(http_requests_total{code=~"5.."}[5m]))
  ```
- 总请求速率：
  ```
  sum(rate(http_requests_total[5m]))
  ```
- 5xx 错误率：
  ```
  sum(rate(http_requests_total{code=~"5.."}[5m]))
  /
  sum(rate(http_requests_total[5m]))
  ```

**3. 关键要点与常见坑**

| 要点 | 说明 |
| --- | --- |
| 用 `rate` 而非原始值 | counter 是累计值，必须转速率 |
| 用正则 `code=~"5.."` | 匹配 500–599 全部 5xx；注意 `code` 标签通常是字符串 |
| 聚合层级要一致 | 两侧都 `sum`，否则按不同标签维度相除会产生错误结果或 NaN |
| 按服务分组 | 想按服务分别看错误率，可在 sum 后加 `by (service)`，两侧要保持一致 |
| 时间窗口 | `[5m]` 表示 5 分钟速率，窗口越长越平滑、响应越慢，可根据告警灵敏度调整 |
| 除以零 | 无流量时结果为 NaN，可在外层用 `or on() vector(0)` 兜底 |

**4. 与课程知识的衔接**

- 这正是前面讲的"黄金信号"中**错误（Errors）**的落地查询，也是 **RED 方法**的 Errors 部分；
- 知识库建议"告警应尽量基于用户影响和错误预算消耗率"，把上面算出的错误率与 SLO 阈值（如 99.9% 可用性 → 错误率不得超过 0.1%）对比，即可驱动告警。

---

示例或练习：

**示例（按服务分组，5 分钟窗口）：**

```promql
sum by (service) (
  rate(http_requests_total{code=~"5.."}[5m])
)
/
sum by (service) (
  rate(http_requests_total[5m])
)
```

含义：统计每个服务的 5xx 错误率（0~1 之间的小数，如 0.012 表示 1.2%）。

**配套告警规则示例（错误率超过 1% 持续 5 分钟告警）：**

```yaml
- alert: High5xxErrorRate
  expr: |
    sum(rate(http_requests_total{code=~"5.."}[5m]))
    /
    sum(rate(http_requests_total[5m])) > 0.01
  for: 5m
```

## T07
结论：
这条 PromQL **目前是不完整、无法解析的**——它存在两处问题：`[abc]` 不是合法的时间窗口，`by (` 子句被截断。作为教学分析，我会先指出它为什么错，再给出修正后的正确写法。

---

步骤/分析：

**1. 逐段拆解这条查询**

`sum(rate(http_requests_total[abc])) by (`

| 片段 | 含义 | 问题 |
| --- | --- | --- |
| `http_requests_total` | 指标名，通常是 HTTP 请求计数的 counter（只增不减的累计值） | 没问题 |
| `[abc]` | 表示"取多长一段时间内的样本"（range vector，如 `[5m]` 表示 5 分钟） | **非法**：`abc` 不是合法时间单位。Prometheus 合法单位是 `s`（秒）、`m`（分钟）、`h`（小时）、`d`（天）等，比如 `[5m]`、`[1h]` |
| `rate(...)` | 把 counter 的累计值转换为每秒增长率 | 因为 `[abc]` 非法，`rate` 的参数不是合法 range vector，整条查询会报解析错误 |
| `sum(...)` | 聚合（把所有序列加总） | 没问题 |
| `by (` | 按某组标签维度分组聚合 | **不完整**：`by` 后面必须跟标签名列表，如 `by (service, code)`，括号未闭合 |

**2. 两个隐藏的学习点**

- **`by` 缺失的后果**：即使把 `[abc]` 改成 `[5m]`，写成 `sum(rate(http_requests_total[5m])) by (` 依然报错——`by` 后至少需要一个标签名。
- **聚合层级一致性**：如果要"按服务分别看错误率"，`sum by (service)` 两侧都要一致（我们在上一题的错误率示例中提过），否则会按错误维度相除产生错误结果。

**3. 修正后的正确写法**

一个合法的、按服务分组计算请求速率的查询：

```promql
sum by (service) (rate(http_requests_total[5m]))
```

如果目标是计算 5xx 错误率（承接上一个问题），完整写法是：


1. **时间先后 ≠ 因果**（05、07 章原文强调"相关不代表因果"）：10:00→10:02→10:05 的顺序只说明"先出现的先出现"，不证明谁导致谁。比如更可能是 10:00 之前某个诱因同时引发三件事。

这是一次典型的"**发布回归 + 告警链路失效**"事故：技术根因大概率在发布变更本身（延迟升高、回滚后恢复，两者共同指向发布是根因），而告警未及时通知则是**放大了影响面**的第二层问题。复盘应无责，把"技术原因"和"流程/可观测性原因"分开记录，并把改进项落实为有负责人、有截止时间的任务。下面按课程 05 章复盘体例给出框架。

## 三、告警流程问题（本次事故的第二条主线）

告警"未及时通知"需要拆成几个环节逐一核对：

1. **检测环节**：延迟升高是否有对应告警规则？
   - 课程 02 章建议：告警应基于**用户影响和错误预算消耗率**，而不是单一 CPU 阈值——如果当时只配了 CPU 告警，延迟类故障可能根本不触发。
   - 课程 06 章：检测延迟（异常发生到告警触发）直接影响 **MTTD**；要区分"检测器发现"与"人工/用户先发现"。
2. **通知/路由环节**：告警触发了但没有及时送达值班人员？
   - 09 章：Alertmanager 负责**分组、抑制、路由**——路由配置错误、值班排班表过期、通知渠道（邮件/IM/电话）故障都可能导致"未及时通知"。
3. **疲劳/淹没环节**：是否因误报过多导致值班人员忽略（06 章"告警疲劳"）？是否被告警风暴淹没（07 章）？
4. **升级机制**：告警发出后长时间未确认，是否有升级（escalation）路径？（合理推断，课程未单列，可按 SRE 最佳实践补充）

**复盘要点**：要把"告警没触发"、"触发了没送达"、"送达了没人看"三种情况区分开——它们是完全不同的修复方向。

## 四、可观测性改进

结合 02、06、09 章，建议改进方向：

1. **告警指标对齐用户体验**：以 P99/P95 延迟、错误预算消耗率为告警核心（02 章），而不是只盯 CPU 等资源指标。
2. **补全检测覆盖**：发布类变更应配套"发布后黄金信号对比"检查（延迟、流量、错误、饱和度四信号全看）。
3. **改进检测灵敏度**：对渐变异常可用 EWMA 等统计方法（06 章），不要只依赖静态阈值；记录检测延迟指标。
4. **告警治理**：控制误报率（优先保 precision，06 章）；对级联告警做拓扑抑制与聚合（07 章案例 3：下游告警在根因告警存在时降级）。
5. **数据治理**：确保指标、日志、链路的服务名/环境/版本标签统一，否则跨源关联无法进行（09 章："数据治理先行于算法"）。
6. **链路追踪**：上线 Jaeger/Tempo 等链路后端，实现跨服务延迟分解——案例 1 正是靠追踪定位到数据库 span。

## T12
结论：
针对"怀疑内存泄漏"，课程知识库给出的最直接线索是：**周期性重启是泄漏的强信号，趋势型指标（线性增长）比瞬时阈值更早暴露问题**（案例 4 复盘要点）。因此整套只读排查方案的核心是：**用趋势和斜率说话，而不是用瞬时值**，并通过"对照"来排除正常波动（如流量、缓存预热、GC 抖动）造成的假象。以下方案全部为只读操作，不修改任何生产配置。

---

步骤/分析：

## 一、需要观察的指标（分四层）

| 层级 | 指标 | 说明与依据 |
| --- | --- | --- |
| **进程内存** | 常驻内存 RSS、堆内存用量（heap used）、非堆内存 | 案例 4 中"内存指标呈线性增长"是典型泄漏曲线；趋势型指标是关键 |
| **容器/平台层** | Pod 内存使用、OOMKilled 事件、重启次数、CrashLoopBackOff | 09 章：K8s 运维重点关注 Pod 状态（OOMKilled）、events；周期性 OOMKill 重启是泄漏的强信号（案例 4） |
| **GC 与运行时** | GC 频率、GC 停顿时长、堆区（Eden/Survivor/Old）分布 | 帮助区分"泄漏"与"GC 参数不合理"；Old 区持续增长而回收不掉是泄漏特征（合理推断，需结合运行环境） |
| **业务/相关性指标** | 请求量 QPS、缓存命中率、本地缓存条目数、线程数 | 用于排除"内存增长只是因为流量增长"的假相关（07 章：相关不等于因果，流量是常见共同诱因） |

## 二、时间窗口（关键设计）

1. **主窗口：覆盖至少 1–2 个完整重启周期**。案例 4 是"每 36 小时 OOMKill 一次"——如果该服务也有周期性重启，观察窗口应覆盖 1–2 个周期（如 72 小时），才能看到"增长→重启→回落→再增长"的锯齿形态。
2. **多粒度观察**：
   - 分钟级：看短期波动和 GC 停顿；
   - 小时/天级：看线性增长趋势；
   - 至少回看 7–30 天历史：定位泄漏是**何时开始**的（对照案例 4 中"发布历史显示近期引入了本地热点缓存"——泄漏往往从某次变更开始）。
3. **关键时间锚点**：记录每次重启（OOMKill）时间点、发布/变更时间点、大促/流量高峰时间点，把内存曲线与这些事件对齐（05 章：先排时间线，标来源与置信度）。

## 三、对照组（排除假象的关键）

内存增长不一定是泄漏，必须用对照排除：

| 对照组 | 对照方法 | 排除的假象 |
| --- | --- | --- |
| **流量对照** | 内存增长斜率 vs 请求量/QPS 增长斜率 | "内存随流量涨"是正常扩容，不是泄漏 |
| **正常时段对照** | 选取历史上无发布、无异常的健康时段，对比内存曲线形态 | 确认增长是近期新出现的异常模式 |
| **同类服务对照** | 对比同集群中**未受变更影响**的其他实例/服务的内存曲线 | 排除平台级问题（如节点内存压力、监控采集偏差） |
| **变更前后对照** | 某次发布前后的内存曲线对比 | 定位泄漏是否由特定变更引入（案例 4 的做法） |
| **GC 后回落对照** | 观察 Full GC 后内存是否回落到健康基线 | 真泄漏：GC 后 Old 区仍持续高位；假象：GC 后正常回落 |

## 四、判定方法（趋势分析，不只靠阈值）

1. **斜率拟合**：对内存时序做线性趋势拟合，观察斜率是否长期为正且不回落（案例 4："线性增长"是典型泄漏曲线）。
2. **检测方法阶梯**（06 章）：静态阈值适合饱和度类指标但易误报；对渐变型泄漏更适合 **EWMA（对近期波动敏感）或 STL 分解（趋势+季节+残差）** 后对残差检测；如有多维指标可考虑 Isolation Forest 等（06 章方法阶梯）。
3. **重启形态**：若出现"每 N 小时 OOMKill → 重启后回落 → 再次线性增长"的锯齿，就是泄漏的强信号（案例 4）。
4. **堆转储对比（只读）**：取两个时间点的 heap dump 做**离线对比**，找出"只增不清"的对象（如案例 4 中"本地缓存 Map 只增不清"）。注意：heap dump 导出属于只读操作，但会占用资源，需在低峰期并由负责人批准后进行。

## 五、停止条件（何时可以下结论）

- **停止条件 1（确认泄漏）**：内存随时间呈持续单调增长，且排除了流量/GC/平台对照组的解释；Full GC 后内存不回落到基线；若观察到周期性 OOMKill 重启则进一步确认。
- **停止条件 2（排除泄漏）**：内存增长与流量增长斜率一致、GC 后正常回落、重启周期与发布/定时任务吻合——则更可能是正常负载或配置问题而非泄漏。
- **停止条件 3（定位根因）**：通过堆转储对比或变更前后对照，找到"只增不清"的具体对象/引入该对象的变更（如无界缓存），形成带证据的候选根因（05 章：至多 3 个候选，附证据/反证/置信度）。
- 在确认根因之前，**不做任何写操作**；确认后如需修复（如加 LRU+TTL、补内存增长率告警），必须走变更审批流程。

## 六、安全边界提醒（只读原则）

- 本方案全部为**只读采集与分析**：查监控、看日志、看事件、导出并离线分析堆转储，均不修改生产。
- **不做**：直接重启服务、改 JVM/容器内存参数、清缓存、扩内存、改告警规则——这些都属于写操作，需审批后执行。
- 堆转储、开启额外 profiling 若影响生产性能，需先做影响评估（如低峰期执行）。
- 注意数据治理：确认该服务在指标、日志、链路中的 service.name/环境/版本标签统一，否则跨源关联不可靠（09 章"数据治理先行于算法"）。

示例或练习：

**对照课程案例 4（内存泄漏的周期性 OOM）**：
- 现象：服务每隔约 36 小时 OOMKill 重启一次，重启后正常。
- 排查：内存指标呈线性增长（典型泄漏曲线）；堆转储对比发现一个本地缓存 Map 只增不清；发布历史显示近期引入"本地热点缓存"但无淘汰策略。
- 根因：无界缓存导致内存泄漏。
- 处置（写操作，需审批后执行）：改为有容量上限的 LRU + TTL；补充内存增长率告警。
- 复盘要点：周期性重启是泄漏的强信号；趋势型指标（线性增长）比瞬时阈值更早暴露问题。

**练习**：如果某服务内存曲线随 QPS 同步上升、GC 后回落到基线、无 OOMKill 重启记录——它更可能是泄漏还是正常负载？（提示：用"流量对照 + GC 回落对照"判断，答案应为"更可能不是泄漏"。）

步骤/分析：

## 一、大白话解释：什么是告警风暴

想象你负责看管一栋大楼的监控室。正常情况下一晚上静悄悄的。某天晚上突然出事了——但其实只坏了一个东西，比如**地下室的水管爆了**。

可是因为水管爆了，水淹了配电室 → 电跳闸了 → 整栋楼黑了 → 电梯停了 → 门禁失灵了 → 每个楼层的应急灯都亮了 → 每间办公室的烟感报警器以为着火全响了。

结果你一晚上收到 200 条报警：漏水、断电、电梯故障、门禁故障、烟感报警……**每一台都在喊"我出事了"**，但它们其实都是同一个根因（水管爆了）引起的连锁反应。这就是告警风暴。

课程资料里就是这么描述的：
> "一次真实故障往往触发几十到几百条告警：数据库慢 → 上游接口超时 → 网关 5xx → 业务告警同时爆发。直接把所有告警交给值班人员会淹没真正的根因。"

翻译一下：数据库变慢 → 依赖它的接口等不及就超时 → 网关报 5xx 错误 → 各种业务报警一起炸。**一条根因，几百条告警。**

## 二、生活化类比：家里的"全家桶警报"

再举个更生活化的例子：

你周末在家，厨房水管爆了。这时候：
- 厨房的水浸报警响了；
- 水漫到客厅，客厅的报警响了；
- 水渗到楼下邻居家，邻居上来砸门；
- 物业打电话来问；
- 手机里各种 App 推送"您家附近水管维修通知"……

**真正的问题只有一个：水管爆了。** 但你被 5 个方向的"警报"同时轰炸，手忙脚乱，可能先跑去关电闸、又去开门、又回微信——反而没第一时间去关总水阀。

告警风暴就是这样：**报警的数量和问题的数量严重不成比例**，一个问题放大成几十上百条噪音。

## 三、为什么它会严重影响值班人员？

| 影响 | 大白话解释 | 课程依据 |
| --- | --- | --- |
| **1. 淹没真正根因** | 几百条告警里只有一两条指向真正的病根，其余都是"连锁反应"。人眼在信息爆炸下很难挑出那一两条。 | 07 章原文："淹没真正的根因" |
| **2. 告警疲劳（狼来了）** | 如果天天几百条报警、大多数是误报或重复，值班人员会逐渐麻木，最后**真的出事时反而没人理**，所有人都在"选择性忽略"。 | 06 章原文："误报过多会导致'告警疲劳'，值班人员开始忽略全部告警" |
| **3. 反应变慢（MTTD 变差）** | 人处理信息有上限。告警越多，从"出事"到"定位到根因"的时间就越长。课程里这个时间叫 MTTD/MTTI——告警风暴会把它拖长。 | 01 章（MTTD 指标）、05 章（诊断顺序） |
| **4. 认知过载、决策瘫痪** | 屏幕上几百条红色告警持续滚动，值班人员会"不知道先处理哪个"，甚至不敢行动——怕处理错。 | 案例 3："夜间 200+ 条告警，值班人员无从下手" |
| **5. 重复和级联噪音** | 同一个故障在每一层（数据库→接口→网关→业务）各报一遍，等于同一条消息换了 4 个马甲发给你。 | 07 章级联描述 |

## 四、课程里是怎么解决这个问题的？（顺带一提）

## 二、安全的只读核查步骤（这些可以做）

在执行任何写操作前，先用只读命令确认现状（课程 09 章关注点：Pod 状态、events、resources requests/limits、探针）：

```bash
# 1. 查看 Deployment 及其副本状态（desired/ready/available）
kubectl get deployment <名称> -n <命名空间> -o wide

# 2. 查看异常 Pod 的详细状态、事件与最近日志（只读）
kubectl describe pod <Pod名> -n <命名空间>
kubectl get events -n <命名空间> --sort-by=.lastTimestamp | tail -50

# 3. 查看资源使用与配额，评估缩容影响
kubectl top pod -n <命名空间>
kubectl get resourcequota -n <命名空间>

# 4. 确认是否有控制器/PDB 保护，评估删除 Pod 是否安全
kubectl get replicasets -n <命名空间> -l <选择器>
kubectl get pdb -n <命名空间>
```

以上均为只读命令，不改变生产状态，风险低，属于课程"优先低风险只读验证"的范畴。

## 三、写操作必须满足的前置条件（缺一不可）

课程 01/03 章与案例 5 给出明确护栏，写操作（删除 Pod、改副本数、动告警）必须：

1. **参数校验**：确认对象名称、命名空间、目标副本数无误；
2. **影响预览**：评估缩容/删除影响面（实例是否在处理流量、是否有 PDB、是否触发级联）；
3. **人工审批**：由有权限的负责人审批，遵循最小权限原则；
4. **幂等控制**：操作可重复、可预期（如通过声明式方式而非一次性命令）；
5. **结果验证**：操作后验证副本恢复、流量正常、告警符合预期；
6. **回滚准备**：明确回滚方案（如恢复原副本数、重新调度 Pod）后再动手；
7. **审计轨迹**：操作留痕，供复盘追溯。

此外，涉及告警的变更还受课程原则约束：告警抑制/关闭应基于"用户影响与错误预算消耗率"审慎设计，而不是为了安静而关闭（02 章）；误报过多要治理规则本身，而不是关掉告警（06 章）。

## 四、正确的推进路径

- 如果是**告警太吵**：优先调阈值/聚合/抑制策略（07 章），而不是关闭抑制。
